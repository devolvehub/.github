# Contributing

Thank you for looking. This guide applies to every repository in this organisation.

## First: check the support level

Every repository states it in the first section of its README.

- **Showcase** — usable, not staffed. Issues are read, an answer is not promised, and a pull
  request may sit. Fork it and go your own way; that is what it is there for.
- **Maintained** — issues and pull requests get a first human reply.

Checking this before you invest an evening is the single most useful thing this guide can tell
you. Nothing here is staffed around the clock, and pretending otherwise wastes your time rather
than ours.

## Opening an issue

A good issue answers three questions: what you did, what happened, and what you expected
instead. A version number and the exact command help more than a description of them.

For anything security-related, do not open an issue — see [SECURITY.md](SECURITY.md).

## Opening a pull request

**Talk before you build anything large.** Open an issue first and describe the change. A pull
request that arrives unannounced and rewrites a design gets declined more often than it gets
merged, and that is a bad outcome for everyone involved.

Small and obvious changes — a typo, a broken link, a clearly wrong default — need no
announcement. Send them.

What a pull request should carry:

- One change per pull request. Two unrelated fixes are two pull requests.
- A description that says what changes and why. The diff already shows how.
- Tests where the repository has them, in the style the repository already uses.
- English throughout: code, comments, commit messages, and the pull-request text itself.

## What to expect

A plain answer, including a plain "no". A change can be declined because it does not fit the
direction of the project, and that is not a judgement of the work. When that happens you will
get the reason rather than silence.
